# Видеофор → Информационное табло

Сервис-интеграция: принимает события от системы видеоаналитики «Видеофор», считает по ним показатели за день и выводит актуальные значения на светодиодное информационное табло.

```
Видеофор ──POST /api/events──> integration-service ──push──> ESP32-шлюз ──> LED-матрица
                                      │
                                  PostgreSQL
```

«Видеофор» — это камеры-детекторы: они не ведут счётчиков, а шлют событие на каждое срабатывание (нарушение, въезд, выезд). Сервис превращает поток событий в показатели и сам решает, когда и что перерисовать на табло.

Пример того, что видит человек на табло:

```
            16.06 14:30   ON
Нарушения за день:        12
Ученики на треке:         16
Инструкторы на треке:      3
```

## Что умеет

- Приём событий по HTTP с аутентификацией по токену.
- Показатели двух типов: `daily` (сбрасывается с новым днём) и `gauge` (текущее значение, переносится между днями).
- Справочник показателей и правил **не зашит в код** — настраивается в рантайме через веб-интерфейс или SQL, без рестарта.
- Веб-интерфейс «Конструктор показателей»: создание, редактирование и удаление показателей, привязка к ним типов событий, настройка вывода (цвета, пороги, верхняя плашка, яркость, колонки).
- Push-модель доставки на табло с фоновыми повторами при сбоях.
- Реестр «необработанных запросов»: неизвестные типы событий регистрируются и сразу видны в конструкторе — под них можно завести показатель в пару кликов.
- Симулятор «Видеофора» для разработки без реального источника событий.

## Быстрый старт

Нужен Docker с плагином Compose.

```bash
git clone <repo> videofor-tablo
cd videofor-tablo
cp .env.example .env
# отредактируйте .env: API_KEY, TABLO_URL, POSTGRES_PASSWORD
docker compose up -d --build
```

Поднимутся два контейнера: `app` (сервис) и `db` (PostgreSQL). Схема БД и начальное наполнение применяются автоматически при старте.

- Веб-интерфейс: <http://localhost:8000/ui/>
- Healthcheck: <http://localhost:8000/health>

С симулятором событий (генерирует случайные события, чтобы увидеть работу без реального «Видеофора»):

```bash
docker compose --profile sim up -d --build
```

Реальное табло при этом всё равно нужно: симулируется только источник событий, `TABLO_URL` должен указывать на шлюз. Если табло недоступно — сервис продолжит работать, события сохранятся, доставка пойдёт фоновыми повторами.

## Конфигурация

Все настройки — через переменные окружения (файл `.env`, см. `.env.example`).

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | — | Пароль PostgreSQL (используется контейнером `db`) |
| `DATABASE_URL` | `postgresql://app:app@db:5432/tablo` | Строка подключения сервиса к БД |
| `APP_PORT` | `8000` | Порт, на котором публикуется HTTP API на хосте |
| `API_KEY` | пусто | Токен входящих событий, заголовок `X-API-Key`. Пусто — приём без аутентификации |
| `APP_TIMEZONE` | пусто | Часовой пояс для границы дня, напр. `Europe/Moscow`. Пусто — системный пояс контейнера (`TZ`) |
| `TABLO_URL` | пусто | Адрес ESP32-шлюза, напр. `http://192.168.0.64` — сюда сервис шлёт HTTP. Пусто — push в лог пропускается |
| `TABLO_TOKEN` | пусто | Токен шлюза (сейчас шлюз без авторизации, зарезервировано) |
| `TABLO_MATRIX_IP` | пусто | IP LED-матрицы, напр. `192.168.0.47`. Нужен только чтобы подключить шлюз к матрице, если связи ещё нет. Уже подключённый шлюз сервис определяет сам — можно оставить пустым. См. ниже |
| `TABLO_MATRIX_PASS` | `guest` | Пароль подключения шлюза к матрице |
| `PUSH_RETRY_SECONDS` | `10` | Интервал фоновых повторов push при недоступном табло |
| `LOG_LEVEL` | `INFO` | Уровень логирования |

### Два адреса: шлюз и матрица

В цепочке два устройства с разными IP, не путать:

- **`TABLO_URL`** — ESP32-шлюз (напр. `http://192.168.0.64`). Это то, **куда сервис шлёт HTTP** (REST + SSE). Шлюз сам ничего не рисует — он мост к матрице.
- **`TABLO_MATRIX_IP`** — сама LED-матрица (напр. `192.168.0.47`), физическая панель. Шлюз запоминает, к какой матрице подключён, и держит связь сам. Сервис на старте читает состояние шлюза через `GET /connect.json` — если тот уже подключён, оттуда же берутся `connected` и размеры панели, и `TABLO_MATRIX_IP` не нужен. Задавать его требуется только чтобы поднять связь с нуля (шлюз отвечает `connected:false`): тогда сервис передаст этот IP шлюзу (`POST /connect.json`).

`TABLO_URL` и `TABLO_TOKEN` можно переопределить в таблице `config` (без рестарта). Параметры подключения к БД — только через переменные окружения.

## Как устроен код

### Поток данных

1. «Видеофор» шлёт `POST /api/events`.
2. Тип события регистрируется в реестре `observed_events` (даже если правила под него нет).
3. По таблице `event_rules` ищутся правила для этого типа (с учётом фильтра по `checkpoint`). Если ни одного — ответ `400`, событие в `events` не пишется, но в реестре остаётся → попадёт в конструктор как «необработанный запрос».
4. Каждое подходящее правило меняет свой показатель операцией `inc` / `dec` / `set`. Одно событие может менять несколько показателей.
5. Событие и новые значения счётчиков пишутся в БД одной транзакцией, обновляется кэш в памяти.
6. Пушер помечается «грязным» (dirty) и фоном отправляет полное текущее состояние на табло.

### Состояние в памяти (`StateCache`)

Текущие значения показателей живут в памяти процесса. В БД сервис ходит только на запись (пришло событие — записали) и при старте/перечитывании справочников. Фоновых опросов БД нет.

- **Старт:** значения за сегодня и справочники (`indicators`, `event_rules`) грузятся из БД один раз.
- **`GET /api/state` и push** читают кэш, в БД не ходят.
- **Смена дня** определяется лениво (`rollover_if_needed`): при первом обращении после полуночи `daily`-показатели обнуляются, `gauge` сохраняют значение. Планировщика нет — границу дня задаёт часовой пояс из конфигурации.
- **Изменение справочников** через API конструктора подхватывается без рестарта функцией `reload_dictionaries`: кэш, правила и конфигурация вывода перечитываются из БД под общим `asyncio.Lock`.

Один процесс uvicorn, один воркер — конкуренции за кэш между процессами нет, нагрузка этого не требует.

### Доставка на табло (`Pusher` + `TabloClient`)

Push-модель. Табло отображает только текущее состояние, поэтому очередь событий не нужна — отправляется полный снимок.

1. Любое изменение помечает состояние dirty (флаг в памяти + `updated_at` в БД).
2. Пушер просыпается по сигналу `asyncio.Event`, собирает области через `render_areas` и шлёт их на шлюз.
3. Успех → `push_state.pushed_at = now()`, флаг снят. Ошибка → состояние остаётся dirty, повтор раз в `PUSH_RETRY_SECONDS`, пока не доставит.
4. Всплески событий коалесятся: не чаще одного обновления в ~2 секунды.
5. Раз в 30 секунд пушер просыпается по таймауту и перерисовывает часы на верхней плашке (если она включена).
6. После рестарта признак dirty восстанавливается из БД сравнением `max(counter_values.updated_at)` за сегодня и `push_state.pushed_at`.

Подключение: при старте клиент открывает SSE-поток к шлюзу и читает его состояние через `GET /connect.json` (`refresh_status`). Источник правды о связи — именно этот запрос: уже подключённый шлюз сразу отдаёт `connected:true` и размеры панели, тогда как SSE-событие `device` может и не прийти. Если шлюз отвечает `connected:false` и задан `TABLO_MATRIX_IP` — клиент поднимает связь (`POST /connect.json`) и перечитывает состояние. `connected` определяется по ответу `GET /connect.json`, не по событию SSE.

Шлюз ESP32 капризный, поэтому клиент (`tablo.py`) соблюдает его ограничения: держит постоянный SSE-поток (без него связь рвётся), шлёт области пачками по 4 с паузой, сериализует запросы, гасит освободившиеся области пустым `msg`. Подробности протокола и причины ограничений — в [`docs/tablo-api.md`](docs/tablo-api.md).

### Рендеринг (`render.py`)

`render_areas` превращает показатели и настройки вывода (`BoardConfig`) в список текстовых областей с координатами, шрифтом и цветом. Здесь же: автоподбор кегля под ширину колонки (чтобы табло не включило прокрутку), раскладка в 1–2 колонки, пороги/градиентная окраска значений, верхняя плашка с часами и индикатором онлайна.

## База данных

PostgreSQL 16, 7 таблиц. Схема применяется при старте сервиса идемпотентным `app/schema.sql`.

| Таблица | Назначение |
| --- | --- |
| `events` | Журнал всех принятых событий с исходным `payload` (JSONB). Источник правды |
| `indicators` | Справочник показателей: `key`, `display_name`, `kind`, `sort_order`, `enabled` |
| `event_rules` | Правила: какой `event_type` (+ опц. `checkpoint`) какой показатель меняет какой операцией |
| `counter_values` | Значения показателей по дням (строка на пару день-показатель). |
| `push_state` | Отметка последней успешной доставки на табло (одна строка) |
| `config` | Параметры рантайма: `display_config`, при желании `tablo_url`/`tablo_token` |
| `observed_events` | Реестр типов событий, которые приходили. Питает «необработанные запросы» в конструкторе |

Добавление показателя не меняет схему — появляются только новые строки. Полное описание полей и DDL — в [`docs/tech-design.md`](docs/tech-design.md), раздел 4.

## Показатели и правила

Показатели не хардкодятся. Начальное наполнение:

| key | display_name | kind | привязанные события |
| --- | --- | --- | --- |
| `violations_day` | Нарушения за день | daily | `violation` → inc |
| `students_on_track` | Ученики на треке | gauge | `student_in` → inc, `student_out` → dec |
| `instructors_on_track` | Инструкторы на треке | gauge | `instructor_in` → inc, `instructor_out` → dec |

**Как добавить показатель.** В конструкторе (`/ui/`) создать показатель и привязать к нему тип события — он сразу появится на табло. То же через SQL:

```sql
INSERT INTO indicators (key, display_name, kind, sort_order)
VALUES ('transport_day', 'Транспорт за день', 'daily', 40);

INSERT INTO event_rules (event_type, checkpoint, indicator_key, op)
VALUES ('transport', 'TK1', 'transport_day', 'inc');
```

Изменения подхватываются на лету (`reload_dictionaries`), рестарт не нужен.

**Как изменить или удалить.** В карточке показателя кнопка **«изменить»** меняет название, тип, порядок и активность (`PATCH /api/indicators/{key}`), **«удалить»** убирает показатель вместе с правилами и историей значений.

Операции правил: `inc` (прибавить `value`), `dec` (отнять, не ниже нуля), `set` (установить). `checkpoint IS NULL` — правило срабатывает на любой точке фиксации; заполненный `checkpoint` — только при совпадении.

## API

Базовый адрес: `http://<host>:<APP_PORT>`. Тела и ответы — JSON.

Аутентификация по токену (`X-API-Key`) проверяется **только** на `POST /api/events` и только если задан `API_KEY`. Остальные эндпоинты (управление через UI) аутентификации не требуют — рассчитаны на доверенную сеть.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/events` | Приём события от «Видеофора» |
| GET | `/api/state` | Текущее состояние показателей |
| GET | `/api/display/config` | Конфигурация вывода + список показателей + параметры панели |
| PUT | `/api/display/config` | Сохранить конфигурацию вывода |
| GET | `/api/display/preview` | Области, которые уйдут на табло (для предпросмотра) |
| POST | `/api/display/push` | Принудительно перерисовать табло |
| POST | `/api/display/clear` | Погасить табло (пауза пушера) |
| GET | `/api/tablo/status` | Статус шлюза: связь, параметры панели, последний push |
| POST | `/api/tablo/reconnect` | Переподключить шлюз (перезапуск SSE) |
| POST | `/api/tablo/brightness` | Яркость экрана `0..255` |
| POST | `/api/state/adjust` | Ручная коррекция счётчика (`key`, `delta`) |
| GET | `/api/event-catalog` | Агрегат для конструктора: события, правила, показатели |
| POST | `/api/indicators` | Создать показатель (опц. сразу с правилом) |
| PATCH | `/api/indicators/{key}` | Изменить показатель |
| DELETE | `/api/indicators/{key}` | Удалить показатель с правилами и историей |
| POST | `/api/event-rules` | Привязать тип события к показателю |
| DELETE | `/api/event-rules` | Отвязать правило (`?event_type=&indicator_key=`) |
| DELETE | `/api/event-catalog/{event_type}` | Убрать тип события из реестра |
| GET | `/health` | Живость сервиса и соединения с БД |

Полный справочник с телами запросов и ответов — в [`docs/api.md`](docs/api.md).

### Пример приёма события

```bash
curl -X POST http://localhost:8000/api/events \
  -H "Content-Type: application/json" \
  -H "X-API-Key: change-me" \
  -d '{
    "event_type": "violation",
    "event_time": "2026-06-16T10:15:00",
    "source": "Videofor",
    "object_type": "transport",
    "checkpoint": "TK1",
    "value": 1
  }'
```

Недоступность табло не считается ошибкой приёма: событие сохраняется, ответ `success`, доставка идёт фоном.

## Разработка

### Локальный запуск без Docker

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# нужен PostgreSQL; задайте DATABASE_URL на свою БД
export DATABASE_URL=postgresql://app:app@localhost:5432/tablo
export API_KEY=dev
uvicorn app.main:app --reload --port 8000
```

Схема БД создастся при старте. Без `TABLO_URL` push'и просто пропускаются (с предупреждением в лог) — удобно для разработки логики без железа.

### Симулятор

`simulator/videofor_sim.py` шлёт случайные события на `/api/events` с интервалом 2–8 с. Запускается профилем `sim` (см. Быстрый старт) или напрямую:

```bash
APP_URL=http://localhost:8000/api/events API_KEY=dev python -m simulator.videofor_sim
```

Среди прочего он шлёт тип `transport` без правила — чтобы показать, как «необработанный запрос» появляется в конструкторе.

### Логи

```bash
docker compose logs -f app   # сервис
docker compose logs -f db    # PostgreSQL
```

Все входящие события и результаты push логируются.
