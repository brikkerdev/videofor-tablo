# Сервис интеграции «Видеофор» и информационного табло. Техническая документация

Версия: 0.2
Дата: 2026-06-10
Основание: docs/tz-tablo-1.md

## 1. Обзор

Сервис принимает события от системы «Видеофор», ведёт счётчики показателей за день и передаёт актуальные значения на информационное табло по его API.

```
Видеофор ──POST /api/events──> integration-service ──push──> Табло
                                      │
                                  PostgreSQL
```

Состав решения:

| Компонент | Технология | Назначение |
| --- | --- | --- |
| integration-service | Python 3.12, FastAPI, uvicorn | Приём событий, подсчёт, push на табло |
| db | PostgreSQL 16 | Хранение событий, счётчиков, конфигурации |

Оба компонента поднимаются через docker-compose. Табло является внешней системой и в состав решения не входит.

## 2. Показатели

Показатели не зашиты в код. Справочник показателей хранится в таблице `indicators`, правила обработки событий в таблице `event_rules` (раздел 4). Новый показатель или новый тип события добавляется SQL-вставкой, без изменения кода и схемы БД.

Атрибуты показателя:

- `key`: машинный ключ;
- `display_name`: текстовая подпись для вывода на табло (табло выводит только текст);
- `kind`: тип подсчёта. `daily`: сброс по календарному дню. `gauge`: текущее значение, переносится между днями;
- `sort_order`: порядок вывода на табло;
- `enabled`: показатель можно отключить, не удаляя.

Начальное наполнение справочника:

| key | display_name | kind |
| --- | --- | --- |
| `violations_day` | Нарушения за день | daily |
| `students_on_track` | Ученики на треке | gauge |
| `instructors_on_track` | Инструкторы на треке | gauge |

Сброс daily-показателей реализован без планировщика: значения хранятся построчно по датам, новая дата создаёт новые строки. Граница дня определяется часовым поясом из конфигурации (`APP_TIMEZONE`). По умолчанию переменная не задана и используется системный часовой пояс окружения, в котором развёрнут сервис (переменная `TZ` контейнера).

## 3. API сервиса интеграции

### 3.1. POST /api/events

Приём события от «Видеофора».

Аутентификация: статический токен в заголовке `X-API-Key`. Значение задаётся в конфигурации сервиса и на стороне «Видеофора». Запрос без токена или с неверным токеном отклоняется ответом 401:

```json
{
  "status": "error",
  "message": "Unauthorized"
}
```

Запрос:

```json
{
  "event_type": "violation",
  "event_time": "2026-06-09T10:15:00",
  "source": "Videofor",
  "object_type": "transport",
  "checkpoint": "TK1",
  "value": 1
}
```

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `event_type` | string | да | Тип события, см. 3.2 |
| `event_time` | datetime ISO 8601 | да | Время события |
| `source` | string | да | Источник, ожидается `Videofor` |
| `object_type` | string | нет | Тип объекта (`transport`, `student`, `instructor`) |
| `checkpoint` | string | нет | Точка фиксации, например `TK1` |
| `value` | integer | да | Значение или признак изменения |

Ответ 200:

```json
{
  "status": "success",
  "message": "Data received and displayed",
  "received_at": "2026-06-09T10:15:05"
}
```

Ответ 400 (ошибка валидации):

```json
{
  "status": "error",
  "message": "Invalid event type"
}
```

Недоступность табло не считается ошибкой приёма: событие сохраняется, сервис отвечает `success`, доставка на табло выполняется фоновым механизмом (см. раздел 5).

### 3.2. Правила обработки событий

Связка типа события с показателем не зашита в код, а хранится в таблице `event_rules` (раздел 4.3). Правило задаёт: тип события, необязательный фильтр по `checkpoint`, целевой показатель и операцию (`inc`, `dec`, `set`).

Начальное наполнение:

| event_type | checkpoint | Показатель | Операция |
| --- | --- | --- | --- |
| `violation` | любой | `violations_day` | inc |
| `student_in` | любой | `students_on_track` | inc |
| `student_out` | любой | `students_on_track` | dec |
| `instructor_in` | любой | `instructors_on_track` | inc |
| `instructor_out` | любой | `instructors_on_track` | dec |

Операция `dec` не опускает значение ниже нуля.

Событие, для которого не нашлось правила, отклоняется ответом 400 `Invalid event type`.

«Видеофор» представляет собой камеры-детекторы с обученными моделями: они не ведут собственных счётчиков, а отправляют событие при каждом срабатывании детектора. Поэтому люди считаются по событиям входа-выхода, текущее число ведёт сервис. Операция `set` остаётся в движке правил на случай источников с готовыми значениями.

Дедупликация не выполняется: уникальный id события в текущем формате не передаётся. Вопрос возвращается в работу, если поле появится в формате «Видеофора».

Пример расширения. Понадобился счётчик транспорта за день по выезду из гаража (ТК1). Изменения кода не требуются, только две вставки:

```sql
INSERT INTO indicators (key, display_name, kind, sort_order)
VALUES ('transport_day', 'Транспорт за день', 'daily', 20);

INSERT INTO event_rules (event_type, checkpoint, indicator_key, op)
VALUES ('transport', 'TK1', 'transport_day', 'inc');
```

Счётчик транспорта находится на уточнении у заказчика и в начальное наполнение не входит.

### 3.3. GET /api/state

Текущее состояние показателей. Служебный эндпоинт для отладки и контроля: табло работает по push-модели (раздел 5).

Список динамический: включённые показатели из `indicators` в порядке `sort_order`.

```json
{
  "date": "2026-06-09",
  "updated_at": "2026-06-09T10:15:05+03:00",
  "indicators": [
    {"key": "violations_day", "display_name": "Нарушения за день", "value": 12},
    {"key": "students_on_track", "display_name": "Ученики на треке", "value": 16},
    {"key": "instructors_on_track", "display_name": "Инструкторы на треке", "value": 3}
  ]
}
```

Табло выводит только текст. Текстовое представление собирается из `display_name` и `value` построчно:

```
Нарушения за день: 12
Ученики на треке: 16
Инструкторы на треке: 3
```

Точный формат текста и способ передачи на табло уточняются после получения спецификации API табло. Сборка текста изолирована в одной функции рендера.

### 3.4. GET /health

Проверка живости. Возвращает `{"status": "ok"}` и статус соединения с БД. Используется healthcheck-ом в compose.

## 4. База данных

PostgreSQL 16. Схема:

### 4.1. events

Журнал всех входящих событий. Источник правды для пересчёта и разбора инцидентов.

```sql
CREATE TABLE events (
    id          BIGSERIAL PRIMARY KEY,
    event_type  TEXT        NOT NULL,
    event_time  TIMESTAMPTZ NOT NULL,
    source      TEXT        NOT NULL,
    object_type TEXT,
    checkpoint  TEXT,
    value       INTEGER     NOT NULL,
    payload     JSONB       NOT NULL,
    received_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_events_event_time ON events (event_time);
CREATE INDEX idx_events_type_time  ON events (event_type, event_time);
```

`payload` хранит исходный JSON целиком. При изменении формата на стороне «Видеофора» данные не теряются.

### 4.2. indicators

Справочник показателей. Определяет, что считается и как подписывается на табло.

```sql
CREATE TABLE indicators (
    key          TEXT PRIMARY KEY,
    display_name TEXT    NOT NULL,
    kind         TEXT    NOT NULL CHECK (kind IN ('daily', 'gauge')),
    sort_order   INTEGER NOT NULL DEFAULT 0,
    enabled      BOOLEAN NOT NULL DEFAULT TRUE
);
```

`daily` сбрасывается с новым календарным днём. `gauge` переносится в новый день из последнего значения предыдущего.

### 4.3. event_rules

Правила: какое событие какой показатель меняет.

```sql
CREATE TABLE event_rules (
    event_type    TEXT NOT NULL,
    checkpoint    TEXT,
    indicator_key TEXT NOT NULL REFERENCES indicators(key),
    op            TEXT NOT NULL CHECK (op IN ('inc', 'dec', 'set')),
    enabled       BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (event_type, indicator_key)
);
```

`checkpoint IS NULL` означает любую точку фиксации. Правило с заполненным `checkpoint` срабатывает только при совпадении. Одно событие может менять несколько показателей: по правилу на каждый.

### 4.4. counter_values

Значения показателей по дням. Одна строка на пару день-показатель.

```sql
CREATE TABLE counter_values (
    day           DATE NOT NULL,
    indicator_key TEXT NOT NULL REFERENCES indicators(key),
    value         INTEGER NOT NULL DEFAULT 0,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (day, indicator_key)
);
```

Обновление атомарно через `INSERT ... ON CONFLICT (day, indicator_key) DO UPDATE`. Строки нового дня создаются лениво при первом обращении: daily с нуля, gauge копированием последнего значения.

Добавление показателя не меняет схему: появляются только новые строки. Заодно таблица даёт историю по дням.

### 4.5. push_state

Отметка последней успешной доставки на табло. Одна строка.

```sql
CREATE TABLE push_state (
    id        SMALLINT PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    pushed_at TIMESTAMPTZ
);
```

Состояние считается недоставленным (dirty), если `max(counter_values.updated_at)` за сегодня больше `pushed_at`.

### 4.6. config

Параметры времени выполнения, изменяемые без перезапуска.

```sql
CREATE TABLE config (
    key        TEXT PRIMARY KEY,
    value      TEXT NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Ключи: `tablo_url`, `tablo_token`, `push_retry_seconds` и прочие по мере необходимости. Параметры подключения к БД задаются только через переменные окружения.

Схема применяется при старте сервиса идемпотентным скриптом `app/schema.sql`: `CREATE TABLE IF NOT EXISTS` плюс сидинг `indicators` и `event_rules` через `ON CONFLICT DO NOTHING` (данные разделов 2 и 3.2). Alembic подключим при первом несовместимом изменении схемы.

## 5. Доставка на табло

Push-модель (подтверждено). После каждого изменения счётчиков сервис отправляет полное текущее состояние (формат раздела 3.3) на API табло. Формат и адрес API табло уточняются, клиент изолирован в модуле `tablo.py`.

### 5.1. Состояние в памяти

Текущее состояние показателей кэшируется в памяти процесса. БД получает запросы только при записи: пришло событие, изменился показатель. Фоновых опросов БД нет.

- Старт сервиса: состояние за сегодня и справочники (`indicators`, `event_rules`) загружаются из БД один раз.
- Событие: запись в `events` и `counter_values` одной транзакцией, обновление кэша.
- `GET /api/state` и push на табло читают кэш, в БД не ходят.
- Изменение справочников в БД подхватывается перезапуском контейнера либо служебным эндпоинтом перечитывания (решим при реализации).

Один процесс uvicorn, один воркер. Конкуренции за кэш между процессами нет, нагрузка этого не требует.

### 5.2. Доставка и повторы

1. Изменение показателя фиксируется в БД и кэше, состояние помечается dirty (флаг в памяти + `updated_at` в БД).
2. Пушер будится сигналом `asyncio.Event` и отправляет состояние. Успех: `push_state.pushed_at = now()`, флаг снимается.
3. Ошибка: состояние остаётся dirty. Пушер повторяет отправку раз в `push_retry_seconds` (по умолчанию 10), пока не доставит. Вне dirty-состояния пушер спит и ничего не опрашивает.
4. Рестарт сервиса: признак dirty восстанавливается из БД сравнением `max(counter_values.updated_at)` и `push_state.pushed_at` (раздел 4.5).

Очередь событий для табло не ведётся: табло отображает только текущее состояние, промежуточные значения ему не нужны.

## 6. Конфигурация (переменные окружения)

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `DATABASE_URL` | postgresql://app:***@db:5432/tablo | Подключение к PostgreSQL |
| `APP_PORT` | 8000 | Порт HTTP API |
| `APP_TIMEZONE` | не задано | Часовой пояс для смены дня. Пусто: системный пояс окружения (`TZ` контейнера) |
| `API_KEY` | нет | Статический токен входящих запросов, заголовок `X-API-Key` |
| `TABLO_URL` | нет | Базовый URL API табло |
| `TABLO_TOKEN` | нет | Токен доступа к API табло, если требуется |
| `PUSH_RETRY_SECONDS` | 10 | Интервал фоновых повторов push |
| `LOG_LEVEL` | INFO | Уровень логирования |

`TABLO_URL` и `TABLO_TOKEN` могут быть переопределены через таблицу `config`.

## 7. Развёртывание

### 7.1. Структура репозитория

```
videofor-tablo/
  app/
    main.py        # FastAPI, эндпоинты, запуск фоновой задачи
    config.py      # настройки из переменных окружения
    models.py      # Pydantic-схемы запросов
    db.py          # asyncpg, запросы
    schema.sql     # схема БД и начальное наполнение
    state.py       # кэш состояния в памяти
    rules.py       # применение event_rules к событию
    render.py      # сборка текста для табло из display_name и value
    tablo.py       # клиент API табло
    pusher.py      # фоновая доставка на табло
  simulator/
    videofor_sim.py  # генератор событий, имитирует Видеофор
    tablo_sim.py     # приёмник push, имитирует табло
  docs/
  Dockerfile
  docker-compose.yml
  .env.example
```

### 7.2. docker-compose

```yaml
services:
  app:
    build: .
    ports:
      - "8000:8000"
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: tablo
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d tablo"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

volumes:
  pgdata:
```

Порт БД наружу не публикуется. Схема БД применяется при старте приложения (раздел 4).

Для разработки есть симуляторы обеих внешних систем, профиль `sim`:

```
docker compose --profile sim up -d --build
```

`videofor-sim` шлёт случайные события в сервис, `tablo-sim` принимает push и печатает текст табло в лог. В `.env` для разработки `TABLO_URL` указывает на `tablo-sim`. При подключении реального Видеофора и табло симуляторы просто не запускаются: без профиля `sim` поднимаются только app и db.

## 8. Логирование и обработка ошибок

- Все входящие события логируются с результатом обработки.
- Невалидный JSON или неизвестный `event_type`: ответ 400 по формату 3.1, событие в журнал ошибок, в таблицу `events` не пишется.
- Недоступность табло: warning в лог, повторы фоновой задачей, приём событий не блокируется.
- Недоступность БД: ответ 503. «Видеофор» отправляет событие один раз и не повторяет, событие в этом случае теряется. Принято как допустимое ограничение. Отсюда повышенное требование к доступности сервиса: `restart: unless-stopped`, healthcheck, БД и сервис на одном хосте.

## 9. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Учёт людей | События входа-выхода. «Видеофор» — камеры-детекторы, своих счётчиков не ведут, шлют событие на каждое срабатывание. Текущее число считает сервис |
| Модель табло | Push: сервис отправляет состояние в API табло |
| Аутентификация входящих | Статический токен, заголовок `X-API-Key` |
| Дубли событий | Не обрабатываются: id события в формате не передаётся. Вернёмся при появлении поля |
| Часовой пояс | Настраиваемый через `APP_TIMEZONE`. По умолчанию системный пояс окружения развёртывания |
| Недоступность сервиса | «Видеофор» шлёт один раз и не повторяет. Потеря события принята как ограничение |
| Транспорт за день | На уточнении у заказчика. В начальное наполнение не входит, добавляется двумя INSERT (раздел 3.2) |
